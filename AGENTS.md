# Agent Router

AI assistants should load skills from `.agents/skills/` based on the task
context. That directory is generated by `pnpm sync:skills`, which restores the
shared skills recorded in `skills-lock.json` and then applies the repo-local
overlays in `.local-agent-skills/skills/`.

Do not hand-edit `.agents/skills/` or `.claude/skills/`. Edit local skills in
`.local-agent-skills/skills/` and re-run `pnpm sync:skills`.
Do not hand-edit `skills-lock.json`; update it with `npx skills add ...` or
`pnpm update:skills` and commit the result.

The postinstall hook attempts to restore shared skills when GitHub auth can
access `OMGWINNING/internal-skills`. Set `SKIP_SKILL_SYNC=1` to skip that local
sync path.

CI should configure git auth for `https://github.com/OMGWINNING/internal-skills`
before install so the postinstall skill restore can validate the committed
`skills-lock.json`.

## Skills Structure

Each skill has:

- `SKILL.md` - Index with description and rule links
- `rules/*.md` - Individual rule files

## Available Skills

**Shared DX Baseline:**

- `git`
- `code-review`
- `lsp-setup`
- `typescript`
- `validation`

**Shared AX Skills:**

- `cli` - CLI command structure, output, errors, configuration, and
  distribution guidance

**Alchemy CLI Local Skills:**

- `changeset` - Create a changeset file for pending user-facing changes

## Skill Loading

Skills are loaded based on the task context:

- Designing or reviewing CLI commands, flags, output, config, help, or install
  behavior -> load `cli`
- Creating release notes or package version changes -> load `changeset`
- Writing TypeScript -> load `typescript`
- Adding or reviewing Zod validation schemas -> load `validation`
- Setting up LSP or code intelligence for an agent -> load `lsp-setup`
- Reviewing a PR/diff for release safety -> load `code-review`
- Working with PR descriptions or lockfile conflicts -> load `git`

## Project Context

This repo contains the Alchemy CLI. It uses TypeScript, Commander, Zod, Vitest,
tsup, Changesets, and pnpm. Preserve the existing terminal output conventions
below when adding or changing commands.

## Alchemy CLI Styling Guidelines

## Goal
Keep all terminal output visually consistent with existing Alchemy CLI conventions used by help, tables, and command output.

## Core Principles
- Prefer shared style helpers in `src/lib/ui.ts`, `src/lib/output.ts`, and `src/lib/error-format.ts` over ad-hoc ANSI strings.
- Use one visual voice: indented blocks, compact spacing, and consistent symbols (`◆` for section headers, `✗` for errors, `✓` for success).
- Keep copy short and actionable.

## Color and Modes
- Human TTY mode: use ANSI styling.
- `--json` mode: no ANSI styling; emit valid JSON only.
- Respect `NO_COLOR`: disable ANSI styling when present.
- If `stderr`/`stdout` is not a TTY, avoid adding terminal-only styling.

## Error Presentation
- All errors should flow through shared formatters.
- Commander parse/usage errors should be formatted via `formatCommanderError()`.
- Application errors should be printed via `printError()`.
- Error blocks should use:
  - red `✗` badge + error label/code
  - red primary error message
  - dim secondary lines (hints, usage details)

## Output Hierarchy
- Section title: branded header style (`◆` + brand color).
- Primary content: normal contrast.
- Secondary/help text: dim.
- Avoid mixing unrelated accent colors in a single block.

## Implementation Notes
- When adding new output, first check whether an existing helper already fits.
- If a new pattern is needed, add a shared helper once, then reuse it.
